Claude Codeを長時間使っていると、こんな経験はありませんか。

- 朝はキレキレだったのに、午後の同じセッションで急に指示を取りこぼすようになる
- さっき決めたはずの方針を平気で無視して、逆のことをやり始める
- 1つ修正を頼んだだけなのに、関係ないファイルまで触り出す
- 同じ説明を何度もし直す羽目になり、だんだん雑な返答になっていく

これは**モデルが急にバカになったわけでも、調子が悪いわけでもありません**。原因はほぼ確実に**コンテキストが溢れている**ことです。

Claude Codeのコンテキストウィンドウは有限です。会話・読み込んだファイル・ツールの実行結果がすべてそこに積み上がっていき、埋まってくると古い情報が薄まり、指示の優先順位がぼやけ、精度が落ちます。長いセッションで賢さが落ちるのは、賢さの問題ではなく**メモリ管理の問題**なのです。

この記事では、コンテキストを意図的に軽く保つための実務テクを**7つの型**として紹介します。`/compact` と `/clear` の使い分け、能動的なコンテキスト管理、調査結果の外部ファイル化など、すべて今日のセッションから試せて、9割は無料機能だけで完結します。

> この記事は「Context Engineering（コンテキストエンジニアリング）」、つまり**LLMに何を覚えさせ何を捨てさせるかを設計する**という考え方の実践編です。プロンプトの書き方ではなく、コンテキストの中身を管理する話です。

---

## まず大前提: コンテキストは「貯金箱」ではなく「作業机」

多くの人がハマる勘違いがこれです。「情報は多く与えるほどAIは賢く判断してくれる」。

実際は逆です。コンテキストは情報をためる貯金箱ではなく、**作業中だけ物を広げておく机**です。机が書類で埋まると、本当に見るべき1枚が他の99枚に埋もれます。

```
コンテキストに積み上がるもの
 ├─ あなたとの会話（往復ぶん全部）
 ├─ 読み込んだファイルの中身（grepやReadの結果も全部）
 ├─ ツールの実行結果（ビルドログ・テスト出力・エラー全文）
 └─ システムプロンプト / CLAUDE.md
```

ポイントは、**いま不要なものほど積極的に捨てる**こと。「念のため残す」が一番効きません。以下の7つの型は、すべて「何を机に残し、何を片付けるか」という同じ思想で貫かれています。

---

## 型1: `/clear` と `/compact` を正しく使い分ける

一番手っ取り早く効くのに、一番使い分けられていないのがこの2つです。両方とも「コンテキストを軽くする」コマンドですが、性質がまったく違います。

| コマンド | 何をするか | 残るもの | 使う場面 |
|---|---|---|---|
| `/clear` | 会話履歴を**まるごと破棄**して空にする | CLAUDE.mdなどの初期設定のみ | タスクが完全に切り替わったとき |
| `/compact` | 履歴を**要約に圧縮**して続行する | 圧縮された文脈の要約 | 同じタスクを続けたいが机が重いとき |

判断はシンプルです。

- **前のタスクの文脈を一切引きずりたくない** → `/clear`
- **同じ作業の続きだが、これまでの経緯は要約で十分** → `/compact`

**よくある失敗:** 別タスクに移ったのに `/clear` せず続けるパターン。たとえば「認証のバグ修正」が終わったあと、同じセッションで「READMEを書く」を始めると、もう不要な認証コードの読み込み結果が机に残ったままになります。READMEを書くのに認証のスタックトレースは要りません。

**Before（タスクをまたいでも片付けない）:**

```
1. 認証バグ修正（src/auth/ を大量に読み込む）→ 完了
2. そのまま「次にREADME書いて」
   → 認証ファイルの中身がコンテキストに居座ったまま
   → READMEに関係ない前提を引きずって精度が落ちる
```

**After（タスクの境目で /clear）:**

```
1. 認証バグ修正 → 完了
2. /clear   ← ここで机をリセット
3. 「README書いて」
   → まっさらな状態で集中できる
```

> 目安: **タスクの「テーマ」が変わったら /clear、テーマは同じで会話が長引いたら /compact**。この一言だけ覚えておけば9割対応できます。

## 型2: `/compact` には「何を残すか」を指示する

`/compact` をただ打つだけの人が多いですが、`/compact` は**引数で「圧縮時に何を優先して残すか」を指定できます**。これを使うかどうかで、圧縮後の精度がまるで変わります。

引数なしの `/compact` は「いい感じに」要約してくれますが、その「いい感じ」があなたの意図とズレることがあります。今まさに重要な決定事項が、圧縮で削られてしまうことがあるのです。

**Before（丸投げ）:**

```
/compact
→ 何が残るかはモデル任せ。直近の細かいやり取りが優先され、
  序盤で決めた「DBはPostgresで統一」という重要方針が薄まることがある
```

**After（残すものを指定）:**

```
/compact これまでの設計判断（DBはPostgres・認証はJWT・APIはREST）と、
未完了のTODOリストを必ず残して。デバッグ中の試行錯誤の詳細は捨ててOK
```

こうすると、要約に「捨ててほしくない芯」が確実に残ります。コツは2つです。

1. **残すもの**を明示する（決定事項・制約・未完了タスク）
2. **捨ててよいもの**も明示する（試行錯誤のログ・もう解決したエラー・読み終わったファイルの中身）

特に2つ目が効きます。「デバッグの途中経過は要らない」と言ってあげると、机から大きなゴミがまとめて片付きます。

---

## 型3: 調査結果は「コンテキスト」ではなく「ファイル」に逃がす

これがContext Engineeringの核心です。**覚えておきたい情報を、コンテキストではなくファイルに書き出す**。

大きな作業の前には必ず「コードベースを調べる」「仕様を整理する」フェーズがあります。ここで読み込んだ大量の情報は、そのままにすると全部コンテキストに積み上がります。しかも調査内容は、その後のセッションをまたいで何度も参照したくなる類のものです。

解決策は、調査結果を**そのセッションのメモリ（コンテキスト）に置きっぱなしにせず、`.md`ファイルに書き出す**ことです。

**Before（調査結果がコンテキストに溜まる）:**

```
「src/ 配下を全部読んで、アーキテクチャを把握して」
→ 数十ファイルの中身がコンテキストに積み上がる
→ そのまま実装に入ると、もう机の半分が埋まっている
→ セッションを閉じたら、せっかくの把握がすべて消える
```

**After（調査結果をファイル化する）:**

```
「src/ 配下を調査して、アーキテクチャの概要を
 docs/architecture-notes.md にまとめて。
 内容は次の3点に絞る:
  1. 主要モジュールの責務（1モジュール2行まで）
  2. データの流れ（リクエスト→DB→レスポンス）
  3. 改修時に注意すべき密結合ポイント
 まとめ終わったら、読み込んだファイルの詳細はもう参照しなくていい」
```

こうすると、

- 調査の**成果だけ**が`docs/architecture-notes.md`に残る
- 次のセッションでは「`docs/architecture-notes.md`を読んで」と言えば、数十ファイルを再読み込みせず把握状態に復帰できる
- コンテキストには「ファイルにまとめた」という事実とその要約だけが残り、机が軽い

**外部ファイル化が効くもの一覧:**

| 情報の種類 | 書き出し先の例 | なぜファイルが良いか |
|---|---|---|
| コードベース調査結果 | `docs/architecture-notes.md` | セッションをまたいで再利用できる |
| 設計判断・決定ログ | `docs/decisions.md` | 「なぜそうしたか」を忘れない |
| 進行中タスクのTODO | `TODO.md` | /compactや/clearで消えない |
| 長い仕様・要件 | `docs/spec.md` | 毎回貼り直さなくて済む |

ポイントは、**コンテキストは揮発する（消える）が、ファイルは残る**という非対称性を利用することです。覚えておきたいものはファイルへ、机の上には「いま触っているもの」だけ。

---

## 型4: ファイルは「全部読む」より「必要な範囲だけ読む」

コンテキストが膨らむ最大の犯人は、実は会話そのものより**ファイルの読み込み**です。1つの大きなファイルを丸ごと読むと、それだけで数百行ぶんの机が埋まります。

Claude Codeに「このファイル読んで」と雑に頼むと、ファイル全体を読み込むことがあります。本当に必要なのが特定の関数1つでも、です。

**Before（丸ごと読む）:**

```
「utils.ts を読んで、formatDate関数を直して」
→ 2000行の utils.ts が全部コンテキストに乗る
→ 使うのは formatDate の20行だけなのに
```

**After（範囲を絞って読ませる）:**

```
「utils.ts の formatDate 関数だけを対象に直して。
 まず grep で formatDate の定義位置を特定してから、
 その関数の前後だけ読んで作業して」
```

明示的に「**まず探してから、必要な範囲だけ読む**」という手順を指示すると、無駄な読み込みが大幅に減ります。これは型3の「外部ファイル化」と並んで、机を軽く保つうえで最も効果が大きいテクです。

> 補足: 大量のファイルを横断調査したいときは、調査自体をサブエージェントに委任して「結果の要約だけ」を受け取るのも有効です。サブエージェントの読み込みは親のコンテキストを消費しないため、机を汚さずに調査できます。

---

## 型5: 長いログ・エラー出力を机に残さない

ビルドログ、テスト出力、スタックトレース。これらは**1回の出力でコンテキストを一気に食い潰す**地雷です。失敗したテストのフルログが数百行、なんてことは普通にあります。

そして厄介なのが、**問題が解決した後もそのログが机に残り続ける**ことです。もう直したエラーのスタックトレースを、その後ずっと抱えて作業する意味はありません。

対策は2段構えです。

**(1) 出力を絞ってから渡す**

エラー全文をそのまま貼るのではなく、要点だけ抜き出すよう指示します。

```
Before: テストのログ全部をコンテキストに取り込ませる
After:  「テストを実行して、失敗したテスト名とエラーの要点
        （メッセージ1行 + 該当ファイル:行番号）だけ報告して。
        スタックトレースの全文は不要」
```

**(2) 解決したら机から下げる**

エラーが直ったら、そのデバッグの試行錯誤は不要です。型2の `/compact` で「デバッグの経過は捨ててOK」と指定して片付けます。

```
（バグが直った後）
/compact バグは修正済み。修正内容（◯◯のnullチェック追加）だけ残して、
デバッグ中の試行錯誤・エラーログは全部捨てて
```

**Before / After で机の重さを比較するとこうなります。**

| | 机に残っているもの |
|---|---|
| Before | 失敗ログ全文 × 5回ぶん + 試したコード全部 + 関係ない読み込みファイル |
| After | 「◯◯のnullチェックを追加して直した」という1行だけ |

## 型6: コンテキストの「重さ」を能動的に監視する

ここまでのテクは、いずれも「机が重くなる前に、または重くなったら片付ける」という能動的な管理です。では、いつ片付ければいいのか。**重くなってから気づくのでは遅い**のが難しいところです。

実務で使える「片付けどき」のサインを挙げます。これらが出たら机が溢れかけている合図です。

```
コンテキスト溢れの黄信号
 ├─ さっき指示したことを取りこぼし始める
 ├─ 序盤で決めた方針と逆のことをやり出す
 ├─ 同じ質問・同じ確認を繰り返すようになる
 ├─ 妙に短く・雑な返答になる
 └─ 「念のため全部読み直します」と無駄な再読み込みを始める
```

これらが1つでも出たら、**タスクが同じなら型2の `/compact`、タスクが変わっているなら型1の `/clear`** を打ちます。我慢して続けても精度は戻りません。

**運用のコツ: 区切りで先回りして片付ける**

黄信号を待つより、作業の自然な区切りで先回りするほうが安全です。おすすめの習慣はこれです。

```
1つの機能・1つのバグ修正が「完了」したら、次に入る前に:
 ├─ 成果と決定をファイルに書き出す（型3）
 ├─ 同じテーマを続けるなら /compact で要約（型2）
 └─ テーマが変わるなら /clear でリセット（型1）
```

「タスクの完了 = 片付けのタイミング」と決めておくと、机が溢れる前に常にリセットがかかります。

---

## 型7: CLAUDE.mdに「重要な前提」を逃がしておく

最後は、そもそもコンテキストに毎回積まなくて済むようにする型です。

毎セッション同じことを説明していませんか。「このプロジェクトはPostgresを使う」「テストは必ずvitestで書く」「コミットメッセージは日本語で」。これらを会話で毎回伝えると、そのぶん机が埋まり、しかも `/clear` するたびに消えて、また説明し直しです。

こういう**変わらない前提**は、会話ではなく `CLAUDE.md` に書いておきます。`CLAUDE.md` はセッションの初期設定として常に読み込まれるため、`/clear` しても消えません。

```
会話に毎回書くべきでないもの（→ CLAUDE.mdへ）
 ├─ 技術スタックの固定事項（言語・DB・フレームワーク）
 ├─ コーディング規約・命名ルール
 ├─ テスト/コミット/PRの運用ルール
 └─ 「触ってはいけないファイル」などの禁止事項

会話で都度伝えるべきもの（→ コンテキストへ）
 └─ いま取りかかっている具体的なタスクの内容
```

つまり**「不変の前提はCLAUDE.mdに、可変のタスクは会話に」**と置き場所を分けます。これで `/clear` を気軽に打てるようになり、型1〜6の片付けがやりやすくなります。

> CLAUDE.mdの中身の設計（何を書き、何を書かないか）はそれ自体が深いテーマなので、ここでは「コンテキストを軽く保つために前提を逃がす器として使う」という観点だけに絞っています。

## まとめ: コンテキストを軽く保つ7つの型

| 型 | 要点 |
|---|---|
| 1. /clear と /compact の使い分け | テーマが変わったら /clear、続きなら /compact |
| 2. /compact に残すものを指示 | 決定事項とTODOを残し、試行錯誤は捨てさせる |
| 3. 調査結果をファイルに逃がす | 揮発するコンテキストでなく、残るファイルに書き出す |
| 4. 必要な範囲だけ読む | 丸ごと読みを避け、探してから狭く読む |
| 5. 長いログを残さない | 出力を絞り、解決後は机から下げる |
| 6. 重さを能動的に監視 | 黄信号で片付け、区切りで先回りリセット |
| 7. 不変の前提はCLAUDE.mdへ | 毎回説明せず、消えない器に逃がす |

長いセッションで精度が落ちるのは、モデルの限界ではなく**コンテキスト管理の設計が抜けている**だけです。机の上を「いま触っているものだけ」に保てば、Claude Codeは長時間でも朝イチのキレを維持してくれます。

7つすべてを一度にやる必要はありません。まずは**型1（/clear と /compact の使い分け）**と**型3（調査結果のファイル化）**の2つだけでも試してみてください。それだけで、午後に急にバカになる現象が体感で減るはずです。
