## こんな「あるある」、ありませんか

- 引き継いだリポジトリ、ファイル数が多すぎて**どこから読めばいいか分からない**
- Claude Code に「このコード説明して」と投げたら、関係ないファイルを延々と読み始めて**コンテキストが一瞬で埋まった**
- 「認証どこ？」と聞いたら**それっぽいけど見当外れの答え**が返ってきた
- 1つのバグ修正の影響範囲が分からず、**怖くて手が出せない**

新規実装より、**他人が書いた大きなコードを理解するフェーズ**でClaude Codeをうまく使えていない人は多いです。本記事は「既存コードの理解・探索」だけに絞り、初見リポの全体像把握 → 検索 → 読解 → 影響範囲特定 → コンテキスト節約までの実用パターンをまとめます。

機能名・コマンドは[Claude Code公式ドキュメント](https://code.claude.com/docs/en/)で確認できる事実のみを使い、確証のないものは書きません。

---

## 探索の基本原則：「全部読ませる」をやめる

巨大コードベースで最初にやりがちな失敗が、**Claudeにファイルを片っ端から読ませること**です。コンテキストウィンドウは有限で、無関係なファイル読み込みはトークンを浪費し、しかもClaudeの性能自体を下げます（公式の大規模コードベースガイドも「defaultが小さいプロジェクト向けにチューニングされているため、巨大リポではコンテキストが無関係な内容で埋まる」と明記しています）。

探索の鉄則は次の3つです。

1. **広く浅く → 狭く深く**。まず構造を1段で掴み、必要な箇所だけ掘る
2. **読み込みは委譲できるなら委譲する**（サブエージェント）
3. **質問は具体的に**。曖昧な依頼は広域スキャンを誘発する

以下、この原則を具体プロンプトに落とします。

---

## STEP 1：初見リポの全体像を1段で掴む

公式の「Understand new codebases」レシピは、リポジトリルートで `claude` を起動して、まず高レベルの概要を聞くことを推奨しています。最初の一言はシンプルでよいです。

```text
give me an overview of this codebase
```

日本語でも構いません。

```text
このコードベースの全体像を概観して。何のためのプロジェクトで、主要なディレクトリの役割は？
```

そこから段階的に掘っていきます。

```text
ここで使われている主要なアーキテクチャパターンを説明して
```

```text
主要なデータモデルは何？
```

```text
認証はどう処理されてる？
```

### ポイント：最初から細部を聞かない

| ❌ いきなり細部 | ⭕ 広く始めて絞る |
|---|---|
| 「`UserService.refreshToken()` の実装を全部説明して」 | 「まず認証まわりの全体像を。その後で `refreshToken` を掘る」 |
| 「全ファイルを読んで仕様書を作って」 | 「主要ディレクトリの役割を1段で。詳細は後で指定する」 |

公式のTipsでも「broad questionsから始めて、specific areasへnarrow downする」「プロジェクト固有用語のグロッサリ（用語集）を頼むとよい」とされています。用語集は特に効きます。

```text
このプロジェクト固有の用語・略語のグロッサリを作って。各用語が定義されている代表ファイルも添えて
```

## STEP 2：検索の指示を上手に出す（Grep / Glob を意識させる）

Claude Code は内部に検索・読み取りツール（コンテンツ検索の Grep、ファイル名パターンの Glob、ファイル読み取りの Read など）を持っています。利用者がやるべきは、**Claudeに「何を探させるか」を明確にする**ことです。

公式の「Find relevant code」レシピは、機能名から入る探し方を推奨しています。

```text
ユーザー認証を扱っているファイルを見つけて
```

```text
これらの認証ファイルがどう連携しているか説明して
```

```text
ログイン処理をフロントエンドからデータベースまで追跡して
```

### Before / After：検索指示の精度

**Before（曖昧 → 広域スキャンを誘発）**

```text
決済まわりどうなってる？
```

**After（探させ方を具体化）**

```text
"checkout" "payment" "stripe" あたりのキーワードでリポジトリを検索して、
決済処理の入口になっているファイルを3〜5個に絞って。
各ファイルの役割を1行ずつで。まだ中身は全部読まなくていい
```

「**まだ全部読まなくていい**」と添えるだけで、無駄な全読み込みを抑えられます。候補を絞ってから読ませるのが基本動作です。

### 型付き言語なら code intelligence プラグインが効く

公式は、TypeScript / Python / Go / Rust 等の言語向けに **code intelligence（コードインテリジェンス）プラグイン**を入れると、テキスト検索ではなく言語サーバ経由で「定義へ移動 / 参照を検索」ができ、不要なファイル読み込みが減ると案内しています。1回の「go to definition」が、grep＋複数ファイル読みの代わりになります。

```text
/plugin install typescript-lsp@claude-plugins-official
```

（プラグインは各言語のlanguage serverバイナリがマシンに必要です。導入可否はチーム事情に合わせてください。）

## STEP 3：アーキテクチャ・依存関係を「言語化」させる

構造の理解は、図やテキストで**書き出させる**と一気に進みます。Claudeはコードを読んだうえで関係を説明できます。

```text
主要モジュール間の依存関係を、Mermaidのflowchartで書いて。
ノードは実在するディレクトリ/モジュール名で。推測した箇所は (推測) と明記して
```

```text
リクエストがHTTP受信からレスポンス返却まで通る層を、
順番にテキストで列挙して。各層の代表ファイルパスを添えて
```

「**推測した箇所は明記して**」は重要です。読んでいない部分を断定で説明されると、後で誤解の元になります。確証がない箇所は分けて書くよう指示しましょう。

データモデルの把握にも使えます。

```text
主要なデータモデル（エンティティ）と、その間のリレーションを表にして。
各モデルが定義されているファイルパスも列に入れて
```

## STEP 4：変更の影響範囲（ブラスト半径）を特定する

「この関数を変えたら、どこが壊れるか」を読み切るのは人力だとつらい作業です。ここはClaudeの得意分野です。

```text
src/utils/auth.ts の verifyToken を変更したい。
この関数を呼び出している箇所をすべて洗い出して、
呼び出し元ファイルと、変更で影響を受ける可能性のある挙動を一覧にして
```

```text
このDBカラムの型を変えると影響が出る箇所（クエリ・モデル・マイグレーション・テスト）を
カテゴリ別に列挙して。確認できなかった領域があればそれも正直に書いて
```

ここでも `@` で対象ファイルを明示すると精度が上がります（後述）。「**確認できなかった領域も書いて**」と頼むと、抜け漏れを自分から申告してくれて安全です。

---

## STEP 5：読み取り専用で安全に探索する（Plan Mode）

「探索中に勝手にファイルを書き換えられたら困る」――そのためのモードがあります。公式の **plan mode** は、Claudeがファイルを読んで計画を提案するが、**承認するまでディスクには一切書き込まない**モードです。

起動時に指定する場合:

```bash
claude --permission-mode plan
```

セッション途中で切り替える場合は `Shift+Tab` でパーミッションモードを循環できます（`default` → `acceptEdits` → `plan` …）。

巨大な未知のコードを最初に探索するフェーズは、plan modeで回すのが安全です。コスト面でも公式が「複雑なタスクの前にplan modeで探索→方針承認しておくと、方向違いの高コストなやり直しを防げる」と推奨しています。

途中で明後日の方向に行き始めたら `Esc` で止めて軌道修正、`/rewind` で会話とコードを前のチェックポイントへ戻せます。

## STEP 6：探索を「サブエージェント」に委譲してコンテキストを節約する

これが大規模探索の最重要テクニックです。**探索はファイル読み込みでメインのコンテキストを汚す**――そこで公式は、探索をサブエージェントに委譲し、**結果（要約）だけ受け取る**ことを推奨しています。

```text
サブエージェントを使って、認証システムがトークンのリフレッシュをどう扱っているか調査して
```

> 公式の表現：サブエージェントは自分のコンテキストウィンドウでファイルを読み、要約を報告する。

つまりサブエージェントが**別のコンテキスト**で大量のファイルを読み、メイン会話には結論だけが返ります。テスト実行・ドキュメント取得・ログ処理など「出力が膨大になる操作」を委譲するのも同じ理屈で有効です。

| | メインで直接読む | サブエージェントに委譲 |
|---|---|---|
| メインのコンテキスト | 読んだファイル全部が乗る | **要約だけ**乗る |
| 向くケース | 1〜数ファイルの精読 | 広域の調査・探索 |

---

## STEP 7：@ 参照で「読ませる対象」をピンポイント指定

Claudeに探させるまでもなく、**読ませたいファイルが分かっている**なら `@` 参照が速くて確実です。

```text
@src/utils/auth.js のロジックを説明して
```

ディレクトリも指定できます（こちらは中身ではなく**ファイル一覧**が入ります）。

```text
@src/components の構成は？
```

公式のTipsより要点:

- ファイルパスは相対・絶対どちらも可
- `@` 参照は、そのファイルのディレクトリと親ディレクトリの `CLAUDE.md` も文脈に追加する
- ディレクトリ参照は**中身ではなくファイル一覧**を見せる
- 1メッセージで複数指定できる（例: `@file1.js と @file2.js`）

「Claudeに探させる（STEP 2）」と「`@`で直接渡す（STEP 7）」は、**対象が分かっているか否か**で使い分けます。分かっているのに探させるのは時間とトークンの無駄です。

## STEP 8：コンテキストを枯らさない運用術

探索は長丁場になりがちです。コンテキスト管理コマンドを覚えておきましょう（公式のコスト管理ガイド準拠）。

| コマンド | 何をするか |
|---|---|
| `/context` | いま何がコンテキストを消費しているかを表示 |
| `/clear` | 無関係な作業に移るとき、文脈をリセットして新規開始 |
| `/compact` | 会話履歴を要約して圧縮。`/compact 〜に注目して` で残す内容を指示できる |
| `/usage` | 現在セッションのトークン使用状況を確認 |

実戦的な使い分け:

- **別タスクに移るとき**は `/clear`。古い文脈は毎メッセージでトークンを食う
- 長い探索の途中でコンテキストが膨らんだら `/compact` で要約を作る。残したい軸を添えると効く

```text
/compact 主要モジュールの依存関係と、認証フローの結論を優先して残して
```

さらに公式が推奨する仕込みとして、**探索結果を会話に残すのでなくファイルに保存する**手があります。長い横断調査ではコンテキストが途中で自動圧縮されるため、「結論はmdに書き出して」と頼んでおくと、会話履歴が圧縮されても成果が残ります。

```text
ここまでで分かったアーキテクチャの要点を docs/architecture-notes.md に書き出して。
後続セッションでこのファイルを読めば文脈を復元できる粒度で
```

次のセッションでは `@docs/architecture-notes.md` を渡せば、ゼロから読み直さずに再開できます。

## STEP 9：CLAUDE.md で「毎回の探索コスト」を下げる

同じリポジトリを繰り返し触るなら、**構造の説明を毎回Claudeに探させるのは無駄**です。公式の大規模コードベースガイドは、リポジトリ構造を `CLAUDE.md` に書いておくことを推奨しています。ルートの `CLAUDE.md` 例（公式より要約）:

```markdown
このリポジトリは packages/ 配下に3パッケージを持つモノレポ:

- packages/api: Express + TypeScript + PostgreSQL のREST API
- packages/web: React + Vite + TypeScript のフロントエンド
- packages/shared: api と web が使う共有ユーティリティ

コマンドはモノレポルートでなく各パッケージのディレクトリで実行すること。
```

公式は次の階層運用も案内しています。

- **ルート `CLAUDE.md`**：リポジトリ全体に効く規約・構成
- **サブディレクトリの `CLAUDE.md`**：その領域固有の規約。Claudeがそのディレクトリのファイルを読むときに**オンデマンドで読み込まれる**

そして「巨大リポでは、起動ディレクトリを絞る（そのパッケージ配下で `claude` を起動する）」と、無関係なサブシステムの `CLAUDE.md` やファイルが文脈に入らず、探索が軽くなります。CLAUDE.md自体は肥大させず**200行以内**を目安に、詳細な手順はスキル等のオンデマンド読み込みへ逃すのが公式の推奨です。

## まとめ：未知の巨大コードに入る順番

1. ルートで `claude`（または対象パッケージ配下で）起動 → `overview` を聞く
2. 用語集とアーキテクチャを**言語化・図化**させる
3. 機能名で**検索させて候補を絞る**（「まだ全部読まなくていい」を添える）
4. 影響範囲は呼び出し元一覧で**ブラスト半径**を可視化
5. 探索フェーズは **plan mode** で読み取り専用に
6. 広域調査は**サブエージェントに委譲**し要約だけ受け取る
7. 対象が分かっているファイルは **`@`** で直接渡す
8. `/context` `/clear` `/compact` で**コンテキストを枯らさない**
9. 繰り返すリポは **CLAUDE.md** に構造を書いて毎回の探索コストを削る

「Claudeにうまく読ませる」の正体は、**読ませる範囲をこちらが設計する**ことです。全部読ませないことが、結果的に一番速くて正確で安いです。
