## あるある課題：ドキュメントは「書いた瞬間が最高品質」で、あとは腐っていく

- README に書いてある起動コマンドが、もう動かない
- 設計書のシーケンス図が、3回のリファクタを経て現実とズレている
- 「このAPIのレスポンス、ドキュメントと違うんだけど？」と言われ、結局コードを読むのが一番早い
- 関数の上のコメントが、関数の中身と矛盾している（しかも誰も直さない）

ドキュメントが腐る理由はシンプルで、**コードは変わるのにドキュメントは追従しないから**です。そして追従しない理由もシンプルで、**手で書き直すのが面倒だから**。

Claude Code は、この「面倒だから後回し」を構造的に潰すのが得意です。ポイントは2つあります。

1. **コードを根拠にドキュメントを生成・更新させる**（記憶や推測でなく、リポジトリの実物を読ませる）
2. **変更とドキュメント更新を1つのワークフローに束ねる**（直したら必ず同期する仕組みにする）

この記事は、その具体的なプロンプトと運用に絞ります。README生成、嘘を書かせないコツ、図の言語化、変更追従、コメント点検、そして腐敗を防ぐ仕組みまで。9割は無料の知識だけで実践できます。

## 1. コードから正確なREADMEを生成させる

「README書いて」と丸投げすると、Claude は一般論で埋めたり、存在しないコマンドを推測で書いたりすることがあります。これを防ぐ鍵は**「読むべき実物を指定する」**ことです。

### Before（推測が混ざりやすい指示）

```text
このプロジェクトのREADMEを書いて。
```

### After（実物を根拠にさせる指示）

```text
README.md を作成して。ただし以下を厳守して。

- 起動・テスト・ビルドのコマンドは package.json の scripts を読んで、実在するものだけを書く
- 環境変数は .env.example と、コード内で process.env を参照している箇所を grep して、
  実際に使われているものだけを列挙する
- ディレクトリ構成は実際の src/ 配下を ls して、実在するものだけ書く
- 推測で機能を盛らない。コードから確認できない内容は書かない
- 確認できなかった項目は README ではなく、最後に「要確認」として箇条書きで報告して
```

ここで効くのが**「実在するものだけ」「確認できなければ要確認として報告」**という縛りです。Claude に「知らないことは書くな、知らないと言え」を明示すると、それらしい嘘（ハルシネーション）が激減します。

### `/init` という出発点

ゼロからCLAUDE.mdを作るなら、公式の `/init` コマンドが使えます。これは Claude がコードベースを解析し、ビルドコマンド・テスト手順・発見した規約を含む CLAUDE.md を生成するものです。既に CLAUDE.md がある場合は、上書きでなく改善提案をします（公式ドキュメント [memory](https://code.claude.com/docs/en/memory) 記載）。

READMEそのものを生成するコマンドではありませんが、「プロジェクトをまず機械に読ませて土台を作る」発想は同じです。土台を作ってから、上記のような縛り付きプロンプトで README を磨くと速いです。

## 2. 「嘘を書かせない」プロンプト設計 — コードを唯一の根拠にする

ドキュメント生成で一番怖いのは、**もっともらしい嘘**です。実在しないオプション、間違ったデフォルト値、存在しないエンドポイント。レビューで気づければいいですが、気づかれず公開されると信頼を失います。

嘘を抑えるプロンプトの型は次の3つです。

| テクニック | 具体的な書き方 |
|---|---|
| 根拠の限定 | 「`src/` 配下のコードと設定ファイルのみを根拠にする。Web知識や一般論で補完しない」 |
| 引用の要求 | 「各記述の根拠となったファイル名と行を、ドラフト段階では併記して」 |
| 不明の明示 | 「確認できない項目は断定せず『未確認』と書く。創作で埋めない」 |

### APIドキュメントを書かせる例

```text
src/api/handlers/ 配下の各ハンドラを読んで、APIリファレンスを api.md に書いて。

各エンドポイントについて:
- メソッドとパスは、ルーティング定義の実コードから取る
- リクエストパラメータは、ハンドラ内で実際に参照しているフィールドだけ列挙する
- レスポンスの形は、return / res.json している実際のオブジェクトから書く
- バリデーションエラーは、実際に投げている箇所から書く

コードに無い項目（例: レート制限）は勝手に書かない。
もし仕様が読み取れないハンドラがあれば、推測で埋めず「要確認」リストに入れて。
```

「実際に参照している」「実際に return している」と動詞を実コードに縛ると、Claude は読みに行きます。逆に「一般的なAPIドキュメントとして」みたいな指示は一般論を呼び込むので避けます。

### Plan Mode で「読んでから書く」を強制する

いきなり書かせず、まず**読ませて計画を立てさせる**と精度が上がります。Plan Mode（Shift+Tab で切り替え）にすると、Claude は調査と計画に徹し、いきなりファイルを書き換えません。「対象コードを全部読んで、ドキュメントの構成案と各セクションの根拠ファイルを先に出して」と頼み、計画を承認してから生成に移ると、根拠の通った文書になります。

## 3. 図・シーケンスを「コードから言語化」させる

設計書で腐りやすい筆頭が図です。手描きの図はコード変更に絶対ついてきません。そこで**テキストで書ける図（Mermaid）をコードから生成**させ、図もリポジトリ管理下に置きます。

```text
src/services/order/ の処理フローを読んで、
注文確定の処理を Mermaid のシーケンス図にして。

- 登場人物（クラス/モジュール）は実在するものだけ
- 呼び出し順は実際の関数呼び出しに沿わせる
- 分岐（在庫不足など）は実コードの条件分岐に対応させる
- コードから読み取れない外部システムは点線+「※未確認」で表現
```

Mermaid ならテキストなので、後述の「変更追従」の対象にできます。図がコードと一緒に diff に乗るので、レビューで「図も直ってる？」を確認できるのが大きい。

アーキテクチャ概要なら `graph TD` でモジュール依存図を、状態を持つ処理なら `stateDiagram` を、と図の種類を指定してあげると安定します。

## 4. 変更時にドキュメントを「追従」させる運用

ここが本丸です。**コードを直したら、同じ流れでドキュメントも直す**。別作業にした瞬間、後回しになって腐ります。

### パターンA：実装とドキュメントを1タスクにまとめる

```text
注文APIに「クーポンコード」パラメータを追加して。
実装が終わったら、同じ変更に紐づくドキュメントも更新して:

- api.md の該当エンドポイントにパラメータを追記
- README の機能一覧に追記が必要か確認
- 関連するコメントが古くなっていないか確認

更新したドキュメントは、必ず今回のコード変更と整合しているか自己チェックして、
矛盾があれば直してから報告して。
```

「実装して終わり」でなく「実装＋ドキュメント整合まで」を1つの依頼にするのがコツです。

### パターンB：diff を根拠にドキュメントを追従させる

変更が一段落したら、差分そのものを読ませます。

```text
git diff main を読んで、この変更で古くなったドキュメントを洗い出して。

- README / docs/ 配下 / 各ファイルのコメントを対象に
- 「この変更で記述が事実と食い違うようになった箇所」を列挙
- 各指摘に、対応する diff の該当箇所を添えて
- 修正案も出して（ただしまだファイルは書き換えず、提案だけ）
```

実装中の頭で書くより、**「変わったもの」を起点にドキュメントを照合**する方が漏れません。提案を確認してから一括反映すれば、レビューもしやすい。

### CLAUDE.md に「同期ルール」を常駐させる

毎回プロンプトで言うのは面倒なので、プロジェクトの `CLAUDE.md` にルールとして書いておきます。CLAUDE.md は毎セッションの冒頭に読み込まれます（[公式ドキュメント memory](https://code.claude.com/docs/en/memory)）。

```markdown
## ドキュメント同期ルール
- 公開API（src/api/）を変更したら、必ず api.md の該当箇所も同じ変更で更新する
- README のコマンド・環境変数は、推測で書かず package.json / .env.example を根拠にする
- ドキュメントに書く内容はコードから確認できる事実に限る。不明は「要確認」と書く
```

CLAUDE.md は**強制ではなく文脈**として効きます（公式が「enforced configuration ではない」と明記）。100%守られる保証はないので、「絶対に外せない」処理は次の Hooks で機械的に担保します。

### ドキュメント特化の規約は `.claude/rules/` に分離する

CLAUDE.md が長くなると効きが落ちます。公式は1ファイル200行以内を推奨。ドキュメント関連の細かい規約は `.claude/rules/` に切り出すと整理できます。さらに `paths` フロントマターで対象ファイルを絞れば、該当ファイルを触るときだけ読み込まれます（[公式ドキュメント memory](https://code.claude.com/docs/en/memory)）。

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API変更時のドキュメント規約
- エンドポイントを追加/変更したら api.md を同じPRで更新する
- レスポンス例は実際の return オブジェクトに合わせる
```

これで「APIコードを触るときだけ、APIドキュメント規約が文脈に入る」状態になります。

## 5. コメントの「過不足」を点検させる

コメントは多すぎても少なすぎても腐敗の温床です。多すぎるコメントはコードとズレて嘘になり、少なすぎると意図が失われます。Claude にレビュー視点で点検させます。

```text
src/services/payment.ts のコメントを点検して。

- コードと矛盾している/古いコメント → 該当行と理由を指摘
- 「何を」しているか書いてあるだけの冗長コメント（コードを読めば分かる）→ 削除候補
- 「なぜ」が必要なのに欠けている箇所（非自明なロジック・回避策・前提）→ 追記候補
- まだ修正はせず、指摘リストだけ出して
```

ポイントは**「何を」より「なぜ」を残す方針を明示**することです。`i++ // iをインクリメント` のような冗長コメントは削除候補に、`// 決済APIが稀に二重応答するためここで冪等化` のような背景は追記候補に分類させます。

### Before / After（点検の指示の質）

| 指示 | 結果 |
|---|---|
| 「コメント増やして」 | 自明な行に冗長コメントが大量発生（むしろ腐敗源が増える） |
| 「コードと矛盾するコメントと、なぜが欠けた箇所を指摘して」 | 直すべき箇所だけが浮かぶ |

## 6. ドキュメント腐敗を「仕組み」で防ぐ

人間の善意（あとで直そう）に頼ると必ず腐ります。仕組みで止めます。

### 仕組みA：スラッシュコマンド化して「いつでも同期」

よく使う同期チェックは、カスタムスラッシュコマンドにしておくと一発で呼べます。`.claude/commands/doc-check.md`（またはスキル）にプロンプトを保存すると `/doc-check` で実行できます。公式によれば、カスタムコマンドはスキルに統合されており、`.claude/commands/deploy.md` と `.claude/skills/deploy/SKILL.md` はどちらも `/deploy` を作ります（[公式ドキュメント skills](https://code.claude.com/docs/en/skills)）。

`.claude/commands/doc-check.md` の例：

```markdown
git diff main を読んで、この変更で古くなった README / docs/ / コメントを洗い出して。
各指摘に diff の該当箇所と修正案を添えて。まずは指摘だけ、修正はしない。
```

これで、PRを出す前に毎回 `/doc-check` を打つだけで照合できます。チームで共有すれば全員が同じチェックを使えます。

### 仕組みB：Hooks で機械的に担保する

「忘れずにやる」を Claude の判断に委ねず、ライフサイクルイベントで強制したいなら Hooks です。Hooks はファイル編集やタスク完了などの時点でシェルコマンドを実行する仕組みで、公式は「LLM の判断に頼らず確実に実行される決定論的な制御」と説明しています（[公式ドキュメント hooks-guide](https://code.claude.com/docs/en/hooks-guide)）。

ドキュメント運用での使い方の例：

- ファイル編集後（PostToolUse）に Markdown のリンク切れチェッカーを走らせ、壊れたリンクを検出する
- 作業終了時（Stop）に「docs/ の更新を確認したか」を通知で知らせる

具体的なコマンドは各プロジェクトの lint ツール次第ですが、「ドキュメント検証を人の記憶でなくイベントで回す」発想が重要です。Hooks の設定方法とイベント一覧は公式の hooks-guide / hooks リファレンスを参照してください。

### 仕組みC：CI で「ドキュメントの鮮度」を落ちないようにする

GitHub Actions など CI 上で Claude Code をヘッドレス実行し、PR の diff に対して「ドキュメント追従漏れ」をコメントさせる運用も可能です。要は**「人がレビューで気づく」を「機械が毎回チェックする」に置き換える**ことです。これだけで、腐敗の進行速度が大きく変わります。

## まとめ：ドキュメントを「コードの副産物」にする

ドキュメントが腐るのは、コードと別管理で、手作業で、後回しだからです。Claude Code を使うなら、逆にします。

- **根拠をコードに縛る** … 「実在するものだけ」「不明は要確認」で嘘を抑える
- **図もテキスト（Mermaid）にする** … diff に乗せて一緒に追従させる
- **変更と同期を1タスクにする** … 「実装＋ドキュメント整合まで」で依頼する
- **規約を常駐させる** … CLAUDE.md と `.claude/rules/` で毎回言わなくていい状態に
- **仕組みで止める** … スラッシュコマンド・Hooks・CI で人の記憶に頼らない

最初の1回、`/init` でCLAUDE.mdの土台を作り、`/doc-check` 相当のコマンドを1つ用意するだけで、「ドキュメントが信用できる」状態に近づきます。腐る前提の運用から、腐らない前提の運用へ。
