Claude Codeをインストールしてみたものの、こんな状態で止まっていませんか。

- 起動はしたが、何を最初に頼めばいいのか分からない
- とりあえずチャットのように使っているが、普通のAIチャットと何が違うのか実感がない
- 「すごいらしい」と聞いて入れたのに、効果がいまいち体感できない
- 設定項目が色々あるが、最初に何をいじるべきか分からない

Claude Codeは**ターミナルで動くAIコーディングエージェント**です。普通のチャットAIと違って、ファイルを読み書きし、コマンドを実行し、複数ステップの作業を自分で進められます。ただし、その力を引き出せるかどうかは**最初の設定**で大きく変わります。

この記事では、Claude Codeをインストールした直後に**最初の30分でやっておくべき設定と使い方**を、順番に手を動かせる形でまとめます。難しい話は後回しにして、まず「実戦で使える状態」に持っていくことを目標にします。

---

## 前提: Claude Codeは「賢いチャット」ではなく「作業する同僚」

最初に頭を切り替えてほしいのがここです。多くの人は最初、Claude Codeをチャットボットのように扱います。「このコードどう思う?」と聞いて、返ってきた文章を自分でコピペする、という使い方です。

それでも動きはしますが、本来の使い方ではありません。Claude Codeは**自分でファイルを開き、編集し、テストを実行し、結果を見て次の手を打てる**エージェントです。つまり「答えを教えてもらう相手」ではなく「作業を任せる同僚」として扱うのが正解です。

| 使い方 | 例 | 評価 |
|---|---|---|
| チャット的 | 「ログイン処理の書き方を教えて」→ 返答を自分でコピペ | もったいない |
| エージェント的 | 「`src/auth/` にログイン処理を実装して、テストも書いて」 | 本来の使い方 |

この違いを意識するだけで、頼み方が変わります。「教えて」ではなく「やって」。これが出発点です。

---

## ステップ1: プロジェクトのルートで起動する（最重要）

意外と見落とされがちですが、**どのディレクトリで起動するか**が最初の分かれ道です。

Claude Codeは起動したディレクトリを作業の起点にします。プロジェクトのルート（`package.json` や `.git` がある階層）で起動しないと、ファイルの位置関係を正しく把握できません。

```bash
# 良い例: プロジェクトのルートで起動
cd ~/projects/my-app
claude

# 悪い例: ホームディレクトリや無関係な場所で起動
cd ~
claude   # どのプロジェクトの話か分からない状態
```

起動したら、まず現状を把握させます。いきなり実装を頼むより、最初に「このプロジェクトを理解して」と言うほうが、その後の精度が上がります。

```
まずこのプロジェクトの構成を把握して。
主要なディレクトリの役割と、使われている技術スタックを
3〜5行で説明して。
```

---

## ステップ2: `/init` でCLAUDE.mdを生成する

Claude Codeには `CLAUDE.md` という仕組みがあります。これは**プロジェクトの取扱説明書**で、起動するたびに自動で読み込まれます。技術スタック・コーディング規約・禁止事項などをここに書いておくと、毎回説明し直す手間がなくなります。

ゼロから書く必要はありません。`/init` コマンドを使うと、プロジェクトを解析して `CLAUDE.md` のたたき台を自動生成してくれます。

```
/init
```

実行すると、プロジェクト構成・使用言語・ビルドコマンドなどを調べて `CLAUDE.md` を作ってくれます。生成されたら、自分の運用に合わせて数行追記しておくと効果が高まります。

```markdown
# CLAUDE.md（追記例）

## このプロジェクトのルール
- パッケージマネージャは npm を使う（yarn禁止）
- テストは vitest で書く
- コミットメッセージは日本語で書く
- `src/legacy/` は触らない（移行中のため）
```

ポイントは、**「毎回口頭で言っていること」をここに移す**ことです。「テストはvitestで」「DBはPostgres」のような毎回の前提を書いておくと、会話がスッキリし、指示の取りこぼしも減ります。

---

## ステップ3: 権限設定で「いちいち確認」を減らす

Claude Codeは、ファイルの編集やコマンド実行のたびに「実行していいですか?」と確認を求めてきます。安全のための仕組みですが、毎回 `y` を押すのは地味にストレスです。

よく使う安全なコマンドは、**事前に許可**しておけます。`/permissions` で設定画面を開けます。

```
/permissions
```

たとえば以下のような読み取り専用・低リスクのコマンドは許可しておくと作業が滑らかになります。

```
許可しておくと快適なコマンドの例
 ├─ npm test / npm run build などのビルド・テスト系
 ├─ git status / git diff などの読み取り系
 └─ ls / cat など状態確認系
```

逆に、**`rm -rf` や `git push --force` のような破壊的・不可逆なコマンドは、許可リストに入れず毎回確認させる**のが安全です。「読み取り・確認系は許可、破壊系は都度確認」という線引きを最初に決めておきましょう。

> 注意: 許可設定はプロジェクト単位で `.claude/settings.json` に保存されます。チームで共有する場合は、メンバー全員が安全だと納得できる範囲に絞ってください。

---

## ステップ4: 大きな作業は「計画させてから」始める

ここからは使い方のコツです。初心者がやりがちなのが、いきなり大きな実装を丸投げすることです。

```
悪い例: 「ユーザー登録機能を全部作って」
→ いきなり大量のファイルを書き始め、想定とズレた実装になりがち
```

おすすめは、**実装の前に計画を立てさせて、それを確認してから着手させる**やり方です。Claude Codeには計画を先に立てるモード（Plan Mode）がありますが、まずは言葉で頼むだけでも十分効果があります。

```
良い例:
「ユーザー登録機能を実装したい。
 まだコードは書かないで。
 まず実装手順を箇条書きで出して。
 それを確認してからGOを出すので、待って」
```

計画を見て「ここは違う」「この順番で」と修正してから着手させると、手戻りが激減します。**「いきなり作らせない、まず計画」**は、最初に身につけるべき習慣のひとつです。

---

## ステップ5: 1タスク終わったら区切りをつける

最後に、長く使うほど効いてくる習慣です。Claude Codeは会話・読み込んだファイル・実行結果をすべて記憶に積み上げていきます。これが溢れると、長いセッションで急に指示を取りこぼし始めます。

対策はシンプルで、**タスクが切り替わったら会話をリセットする**ことです。

| コマンド | 何をするか | 使う場面 |
|---|---|---|
| `/clear` | 会話履歴をまるごと破棄する | 別のタスクに移るとき |
| `/compact` | 会話履歴を要約に圧縮する | 同じ作業を続けるが会話が長くなったとき |

「認証のバグ修正が終わった → 次はREADMEを書く」のようにテーマが変わるときは `/clear`。同じ作業の続きで会話が長引いたら `/compact`。この使い分けを覚えておくと、午後に急に精度が落ちる現象をかなり防げます。

---

## まとめ: 最初の30分でやることチェックリスト

| ステップ | やること | 所要 |
|---|---|---|
| 1 | プロジェクトのルートで起動し、構成を把握させる | 5分 |
| 2 | `/init` で CLAUDE.md を生成し、ルールを数行追記 | 10分 |
| 3 | `/permissions` で安全なコマンドを許可、破壊系は都度確認 | 5分 |
| 4 | 大きな作業は「まず計画」を立てさせてから着手 | 習慣 |
| 5 | タスクの区切りで `/clear` か `/compact` | 習慣 |

Claude Codeは、最初に少し設定を整えるだけで体感がガラッと変わります。特に**ステップ2のCLAUDE.md**と**ステップ4の計画ファースト**は、今日から効果を感じられるはずです。

まずはインストール済みのプロジェクトを1つ開いて、`/init` から始めてみてください。それだけで「とりあえず動かす」から「実戦で使える」に一歩進みます。
