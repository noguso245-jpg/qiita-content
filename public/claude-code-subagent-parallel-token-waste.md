サブエージェントを並列でたくさん走らせると、調査は速くなる——けれど、ある日トークンの消費だけが妙に膨らんでいることに気づきます。この記事は、その「並列にしたら速くなったが、コストが跳ねた」を**同時実行の絞り込み**と**重複調査の排除（dedup）**で抑える話です。

Claude Code（Anthropicの公式CLI）でサブエージェントを並列に使うと、最初は「速い・気持ちいい」が先に来ます。複数の対象を複数の子に割り当てて一気に調べさせる（実際の同時実行数は環境やセッションの状況に依存します）。

ところが、横断調査を何度も回しているうちに、こういう引っかかりが出てきます。

- 対象が30個あるからと、勢いで30体ぶん投げる
- 別々の子が、**結局おなじファイル・おなじフォルダを読んでいる**
- 「サービスA」と「service_a」を別物として2回調べさせていた
- 親はもう答えを知っているのに、子はゼロから読み直して同じ結論を出す

調査結果は正しい。でも、**同じ読み込みを人数ぶん払っている**。並列化の速さと引き換えに、トークンだけが静かに膨らむ——これは「サブエージェントを並列で使おう」という記事ではあまり触れられない、回数を重ねると必ず当たる壁です。

この記事では、筆者がサブエージェントで横断調査（多数のファイル・フォルダ・サービスの棚卸し）を回すなかで効いた、**無駄トークンを減らす2つの型**を紹介します。コードを書かせる用途ではなく、「読む・調べる・要約する」をエージェントに任せるときの話です。

---

## なぜ無駄が出るのか：トークンは「人数 × 各自が読む量」で効く

サブエージェントは、それぞれが独立したコンテキストを持って動きます。親に返ってくるのは最終報告だけでも、**子は調査の過程で対象を自分で読み込んでいて、その読み込みぶんのトークンは確実にかかっています**。

つまり、並列調査のコストはざっくり **「子の人数 × 各自が読む量」** で効きます。ここから無駄の出どころは2つに整理できます。

1. **投げすぎ（過剰な並列）** — 対象が30個あるからと機械的に30体に割る。1体あたりの調査が薄いのに、起動と前置きのコストだけ人数ぶんかさむ。
2. **重複調査** — 担当範囲を分けていないので、複数の子が**同じファイルを別々に読む**。同じ場所を2体が読めば、答えが同じでも読み込みは2回ぶん課金される。

賢さの問題ではありません。**「誰に・何を・重複なく割り当てるか」を設計していない**のが原因です。

---

## 型1：同時実行数を絞る（対象の数だけ投げない）

「対象が多い＝子も多く」ではありません。**重い実体の単位でまとめて**、起動する子の数自体を減らします。

### Before（対象の数だけ投げる）

```text
30個のフォルダを、それぞれ別のサブエージェントに調べさせる。
```

→ 1体あたりは数分の浅い調査。なのに30回ぶんの起動・前置き・コンテキスト読み込みが乗る。軽い対象まで1体ずつ割ると、割に合わない。

### After（まとめて投げて、子の数を抑える）

```text
30個のフォルダを、関連の近いもので5グループにまとめる。
1体のサブエージェントに1グループ（6フォルダ）を渡し、
グループ内をまとめて調べて1つの報告にして返させる。
```

ポイントは、**1対象=1エージェントを当たり前にしない**こと。対象が軽いなら束ねて1体に持たせ、重い対象（読む量が多い・判断が要る）だけ単独で割り当てる。同時に走る子の数を抑えるだけで、起動コストの重複が減ります。

> もちろん絞りすぎれば直列に近づいて遅くなります。これは速度とコストのトレードオフで、**「軽い対象は束ねる／重い対象は分ける」**のさじ加減が現実解です。締め切りが近いタスクは並列寄り、コスト重視の棚卸しは束ね寄り、と目的で振り分けると決めやすい。

## 型2：重複調査を弾く（dedup）

並列の無駄でいちばん効くのが、**同じものを2回調べさせない**ことです。やることは3つ。

### (1) 投げる前に対象リストの重複を消す

fan-outの前に、対象リストを正規化して重複を落とします。地味ですが、ここで弾けるなら一番安い。

- 同じ実体を指す**別名・別パス**を1つに寄せる（`サービスA` と `service_a`、末尾スラッシュ違いのURL など）
- 同じファイルへのシンボリックリンク・ショートカットを二重に数えない
- 「もう調べ済み」の対象を今回のリストから外す

リスト整理は親側（あなた、またはコード）でやるのが安全です。**dedupまでサブエージェントに任せると、その判断のために結局全部読ませることになり**、本末転倒になりがちです。

### (2) 担当範囲を排他的に割り当てる

複数の子に投げるなら、**範囲が被らないように切って**渡します。

```text
子A: public/ 配下「だけ」を調査（queue/ には触れない）
子B: queue/ 配下「だけ」を調査（public/ には触れない）
```

「だけ」「触れない」を明示するのがコツ。曖昧だと、親切心で隣の範囲まで読み始めて重複が復活します。

### (3) 既知の情報は渡して、ゼロから読み直させない

親がもう知っていることを子に渡せば、子はそこを読み直さずに済みます。

```text
（前回の調査で判明している前提を先に渡す）
- このフォルダ群はすべて稼働中だと確認済み
- 最終更新日は別途取得済みなので調べ直さなくてよい

今回知りたいのは「各フォルダのブロッカー」だけ。そこに絞って調べて。
```

「全部調べて」ではなく **「ここは済み・知りたいのはこれだけ」** と差分で頼む。読む量そのものが減るので、人数を変えなくてもトークンが落ちます。

## なぜこれが効くのか

| 打ち手 | 効く理由 |
|---|---|
| 軽い対象を束ねる | 起動・前置きの重複（人数ぶん）を減らせる |
| リストを先にdedup | 同じ対象を2回読む課金を、投げる前に消せる |
| 排他的に範囲を割る | 子どうしの読み込みが被らない＝重複ゼロ |
| 既知情報を渡す | 各自が読む量が減る（人数を変えずにコスト減） |

コストは「人数 × 各自が読む量」。型1は**人数**を、型2は**各自が読む量と重複**を削ります。両方を効かせると、調査の速さは保ったまま、消費だけを落とせます。

---

## 落とし穴：dedupと絞り込みは「やりすぎ」が逆に痛い

無駄を削るのは効きますが、削りすぎると別の事故になります。

- **絞りすぎて直列化** — 子を減らしすぎると並列の旨味が消える。重い対象まで束ねない。
- **dedupの取り違え** — 似て非なる対象を同一視して片方を捨てると、**取りこぼし**になる。「サービスA」と「サービスA2」は別物かもしれない。正規化キーは慎重に。
- **排他分割の境界抜け** — 範囲を「だけ」で割ると、どの担当にも入らない隙間の対象が出ることがある。割り当て後に**対象の総数が合っているか**を必ず数える。
- **既知情報の渡しすぎで誤誘導** — 「稼働中と確認済み」と渡したのが実は古い情報だと、子はそれを前提に進んでしまう。渡す前提は鮮度を確認する。

削減は「速度」と「取りこぼし」とのトレードオフです。**何を削ったかを親が把握できる範囲で**削るのが安全です。

## まとめ

| 型 | 要点 |
|---|---|
| 同時実行を絞る | 1対象=1エージェントにしない。軽い対象は束ね、重い対象だけ分ける |
| 先にdedup | 投げる前に対象リストの別名・重複・調査済みを消す |
| 排他的に割る | 「ここだけ／隣は触れない」を明示し、割り当て後に総数を数える |
| 既知情報を渡す | 「ここは済み・知りたいのはこれだけ」と差分で頼む |

サブエージェントの並列は「たくさん走らせる」だけだと、速さと引き換えにトークンを取りこぼします。**誰に・何を・重複なく割り当てるか**を設計して初めて、速さとコストを両立できます。

## まず1つだけ試すなら

全部を一度にやる必要はありません。次に並列調査を投げる前に、これだけやってみてください。

```text
1. 対象リストをざっと見て、明らかな重複（別名・別パス・調査済み）を消す
2. 軽い対象は数個ずつ束ねて、子の数を減らす
3. 各子に「この範囲だけ／隣は触れない」と明示して渡す
```

これだけで、同じ調査でも読み込みの重複が減り、消費が目に見えて落ちます。まずは小さな横断調査から試してみてください。
