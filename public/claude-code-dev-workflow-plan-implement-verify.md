## はじめに：なぜAIに任せると「惜しい」結果になるのか

Claude Code（Anthropicの公式CLI）を使い始めて、こんな経験はないでしょうか。

- 「ログイン機能を作って」と頼んだら、それっぽいコードは出てきたが、自分のプロジェクトの書き方とは全然違う
- 一度の指示で大量のファイルを書き換えられ、どこが変わったのか追えなくなった
- バグを直してと頼むたびに別の場所が壊れ、いたちごっこになる

これは「AIの性能が低い」から起きるのではありません。多くの場合、**AIに渡している前提情報と進め方の設計が足りていない**のが原因です。

人間の新人エンジニアに「いい感じにやって」とだけ伝えても、いい感じにはなりません。コーディング規約、ディレクトリ構成、テストの流儀を共有し、「まず設計を見せて」「小さく出して」と進め方を決めるはずです。AIエージェントに対しても同じ「型」が必要です。

この記事では、筆者がClaude Codeを日常的に使うなかで効果を感じている **「計画 → 実装 → 検証」の開発ワークフロー** を、今日から真似できる具体的なやり方として紹介します。読み終えたら、手元のプロジェクトで1つ試せる状態になることを目指します。

---

## 開発の型の全体像：Plan → Implement → Verify

実装タスクを丸投げするのではなく、3つのフェーズに分けて進めます。

1. **Plan（計画）**：いきなりコードを書かせず、まず「何をどう変えるか」を言葉と手順で出させる
2. **Implement（実装）**：合意した計画にそって、小さい単位で変更させる
3. **Verify（検証）**：変更が意図どおり動くかを、テストや実行で必ず確かめる

ポイントは、**フェーズの境目に人間のチェックを挟む**ことです。計画を読まずに実装に進ませない。検証せずに「完了」と言わせない。この区切りが、暴走と手戻りを大きく減らします。

以降、フェーズごとに具体的な渡し方を見ていきます。

---

## Plan：いきなり書かせず、まず計画を出させる

最も効果が大きいのが、この最初のひと手間です。

タスクを伝えたあと、**「実装はまだしないで。まず変更計画だけ出して」** と一言添えるだけで、AIの動き方が変わります。実際には次のように指示します。

```text
ユーザー認証にレート制限を追加したい。
まだコードは書かないで。先に以下を出してほしい:
1. 変更が必要なファイルの一覧と、それぞれ何を変えるか
2. 想定する副作用・既存への影響
3. 確認したい不明点があれば質問
```

こう頼むと、AIは「どのファイルを触り、何を前提にしているか」を先に言語化します。ここで読むと、

- そもそも触ってほしくないファイルが対象に入っている
- 自分の意図と違う設計を前提にしている
- 自分も気づいていなかった考慮漏れ（例：既存テストへの影響）

といったズレを、**コードが1行も書かれる前に**修正できます。実装後に気づくと巻き戻しが大変ですが、計画段階なら一言で直せます。

> コツ：計画に納得できないときは、合意できるまで実装に進ませないこと。「2番の影響範囲が不安。先にそこだけ調べて」のように、計画を往復で詰めるのが安全です。

## CLAUDE.md：プロジェクトの「前提」を一度書いて使い回す

毎回口頭で規約を伝えるのは非効率です。Claude Codeには、プロジェクトルートに `CLAUDE.md` を置くと、その内容を前提として読み込んでくれる仕組みがあります。ここに「このプロジェクトの当たり前」を書いておくと、毎回の指示が短くなり、出力のブレも減ります。

最小構成の例です。

```markdown
# CLAUDE.md

## このプロジェクトについて
- Next.js (App Router) + TypeScript の Web アプリ
- パッケージマネージャは pnpm を使う（npm/yarn は使わない）

## コーディング規約
- コンポーネントは関数コンポーネントのみ。class は使わない
- 型は any を避け、unknown + 絞り込みで書く
- 既存の命名・ディレクトリ構成に合わせる。新しい流儀を勝手に導入しない

## 進め方のルール
- 大きな変更の前に、まず変更計画を出す（いきなり実装しない）
- 1コミットで複数の無関係な変更を混ぜない
- 変更後はテストを実行し、結果を報告する
```

書くときのコツは3つです。

- **「やること」より「やってほしくないこと」を明記する**：「class は使わない」「勝手にライブラリを追加しない」のような禁止事項は、暴走の予防に効きます
- **抽象論を避け、具体的に書く**：「きれいに書く」ではなく「any を避ける」「pnpm を使う」のように検証可能な形にする
- **育てる前提で小さく始める**：最初から完璧を目指さず、「またズレたな」と思ったルールを1行ずつ足していく

このファイルは「AIへの引き継ぎ書」であると同時に、人間の新メンバーにとっても読みやすいドキュメントになります。

## Implement：小さく出させて、差分を読む

計画に合意したら、実装に進みます。ここでの原則は **「小さく出させる」** です。

一度に10ファイルを書き換えられると、レビューが追いつかず、結局ほとんど読まずに受け入れてしまいます。それでは品質を担保できません。次のように区切ると、各ステップの差分を無理なく読めます。

```text
計画OK。ではステップ1だけ実装して。
ステップ2には進まず、いったん差分を見せて。
```

そして、出てきた差分は **必ず自分の目で読む** こと。AIが生成したコードを読まずにマージするのは、知らない人のPRをノールックでmergeするのと同じです。読むことで、

- 規約違反（CLAUDE.mdに書いたはずのルールから外れていないか）
- 余計な変更（頼んでいないリファクタが混ざっていないか）
- 理解できない箇所（自分が説明できないコードは、後で必ず負債になる）

を早期に拾えます。読んで「なぜこう書いたの？」と聞き返すこと自体が、AIの軌道修正になります。

## Verify：診断を実装と切り分ける

最後の検証フェーズ。ここで強くおすすめしたいのが、**バグ調査のときは「直して」ではなく、まず「診断だけして」と頼む**という進め方です。

「このエラーを直して」と頼むと、AIは原因を特定する前に当て推量で修正を始めがちです。結果、症状が消えても根本原因が残り、別の形で再発します。そこで、修正と原因究明を分けます。

```text
このエラーが出ている（ログを貼る）。
まだ修正はしないで。
原因として考えられる箇所を、根拠（どのコードのどの挙動か）つきで挙げて。
コードは変更しないこと。
```

こうすると、AIは「どこが原因か」の仮説を根拠つきで出します。人間はそれを読んで、もっともらしい仮説に絞ってから「ではその箇所だけ直して」と進めます。**診断と修正を分けるだけで、的外れな変更が激減します。**

そして修正後は、必ず動作確認まで含めて閉じます。

```text
修正したら、関連するテストを実行して結果を報告して。
落ちたテストがあれば、まず原因を説明してから直して。
```

「動いたはず」で終わらせず、テストや実行で裏を取る。この一手間が、後からの手戻りを防ぎます。

## まず1つだけ試すなら

全部を一度に取り入れる必要はありません。効果を実感しやすい順に、1つずつで十分です。

1. **次の実装依頼で「まず計画だけ出して」と言ってみる**（今日からできて、効果が一番分かりやすい）
2. **プロジェクトに最小の `CLAUDE.md` を置く**（10行で十分。ズレたら足す）
3. **バグ調査を「診断だけ」と「修正」に分ける**

この3つだけでも、「惜しい結果」が「使える結果」に変わる場面が増えるはずです。AIの賢さに任せきるのではなく、人間が型と区切りを設計する——それがエージェントを戦力にする近道だと、筆者は考えています。
